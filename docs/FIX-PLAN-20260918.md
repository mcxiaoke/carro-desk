## 2. 需要修正或降级的报告结论（6 条，其中 2 条为实质性误判）

### 2.1 ❌ bd A6 「`IdleDetector.cs` 全仓无引用，应删除」——不成立，按原方案执行会编译失败

bd 结论：`src/Services/IdleDetector.cs`（154 行）全仓零引用，直接删除。

实测：

```
src/Services/Tasks/TaskConditionEvaluator.cs:21:
    uint idleMs = IdleDetector.GetIdleMilliseconds();
```

`TaskConditionEvaluator` 是 `when.onlyIdle` 条件的判定实现，**仍在生产路径上**（`RunManual` / `ExecuteAsync` 都调用 `ShouldRun`）。

**正确的处置**：`IdleDetector` 是**半死代码**——
- 活的部分：`public static uint GetIdleMilliseconds()`（`IdleDetector.cs:97-104`）；
- 死的部分：整个实例状态机（`_timer/_fired/_warned/_effectiveMs/_lastRaw`、`Start/Stop/Reset/Suspend`、`ThresholdReached/Warning` 事件、`ShouldSuspend`、`IsSystemBusy()`）——这些语义已被 `SystemIdleService` + 各模块内复刻逻辑取代。

**建议**：删除实例状态机，把 `GetIdleMilliseconds()` 迁到独立的 `NativeIdleApi`（或 `ProcessHelper` 同级的 `NativeHelper`），`TaskConditionEvaluator` 改引用新位置。若只删文件不迁移，`dotnet build` 必挂。

### 2.2 ⚠️ bd A5 / gm 2.3 「未初始化模块被 Start 后 `NullReferenceException` 导致启动崩溃」——严重度需降级

两份报告都判定该洞会导致"启动崩溃"。实测 `Core/ModuleBase.cs:38-57`：

```csharp
public void Start()
{
    if (Status == ModuleStatus.Faulted) return;   // 只拦 Faulted
    if (IsRunning) return;
    try { OnStart(); IsRunning = true; Status = ModuleStatus.Running; }
    catch (Exception ex)
    {
        Status = ModuleStatus.Faulted;            // ← 异常在此被吞并降级
        Context?.GetService<ILoggerService>()?.LogError(Id, "启动模块时发生异常", ex);
    }
}
```

`OnStart()` 里 `Context.GetService<>()` 抛的 NRE 会被 `ModuleBase.Start` 捕获 → 模块置 `Faulted` + 记日志。**不会崩进程**，表现是"该模块静默不可用"。

**结论**：契约洞真实存在（应修），但优先级从 bd 的 P1 降到 **P2**；gm 的"启动崩溃"表述属高估。

### 2.3 ⚠️ gm 缺陷 3 「白名单模式下前台应用被静音」——结论对，但引用的代码路径不是根因

gm 引的是 `EvaluateForeground` 的 `else` 分支（`:196-204`）启动静音计时器，据此推断"前台应用被静音"。但真正执行静音的是 `OnMuteTimerTick`（`:206-239`），其白名单分支显式排除了当前前台：

```csharp
// :214-225
foreach (var proc in activeProcs)
    if (!ProcessHelper.ContainsProcess(Config.TargetApps, proc)     // 不在白名单
        && !ProcessHelper.IsMatch(proc, currentFore))              // 且不是当前前台 ← 前台被排除了
        _audioService.SetProcessMute(proc, true);
```

所以走"静音"路径时前台确实不会被静音。**真正的根因在解静音路径**：

```csharp
// :241-251  OnUnmuteTimerTick —— 唯一会 SetProcessMute(x, false) 的地方
if (!string.IsNullOrEmpty(_lastTargetProc)) _audioService.SetProcessMute(_lastTargetProc, false);
```

而 `_lastTargetProc` **只在 `isTarget == true` 分支被赋值**（`:193`）。于是在白名单模式下：

1. 非白名单应用（如 Chrome）在后台 → 被 `OnMuteTimerTick` 静音；
2. 用户切回 Chrome 前台 → `isTarget == false` → 走 `else`，**不启动解静音计时器**；
3. `OnMuteTimerTick` 的白名单分支只做 `SetProcessMute(proc, true)`，**从不解静音**；
4. ⇒ Chrome 保持静音，前台也不出声。✅ 用户可见现象与 gm 一致，但**修复点应在"前台变更/静音 tick 时对当前前台无条件解静音"**，而不是改 `EvaluateForeground` 的分支。

**对照**：黑名单模式无此问题——前后台切换都会走 `isTarget` 分支并正确解静音。

### 2.4 ⚠️ gm 缺陷 2 「FloatingPanelWindow 打开 N 次累积 N 个监听，事件雪崩 + 无法 GC」——机制不成立，降级为 P2 设计加固

gm 判定：`node` 是"各业务模块长期存活的菜单模型对象"，每次 `RebuildMenu` 都在同一对象上叠加匿名订阅。

实测 6 个模块的 `GetTrayMenuItems()` **每次调用都 `new` 全新节点树**，模块缓存的 `_trayRoot` / `_toggleItem` / `_trayItem` 字段只保留**最新一代**：

| 模块 | 节点创建方式 |
|---|---|
| `ScreenLockModule.cs:319-382` | `new TrayMenuItem{...}` + 全部子项现建 |
| `TaskSchedulerModule.cs:137-258` | 同上 |
| `AudioSwitchModule.cs:305-340` | 同上（含设备列表逐项现建） |
| `AppAutoMuteModule.cs:272-314` | 同上 |
| `AwakeModule.cs:319-456` | 同上 |
| `MonitorProfileModule.cs:234-358` | 同上 |

⇒ 旧节点在 `ItemsHostMenu.Items.Clear()` 后失去所有强引用（模块字段已被覆盖），连同其匿名订阅一起可回收。**不存在 N 次累积**，也不会阻断窗口 GC（`FloatingPanelWindow` 本身是 `_instance` 单例，本来就不回收）。

**但确实存在两个真实隐患**，故不整体否定，而是改判为设计加固项：

1. `node.Children.CollectionChanged += ...`（`FloatingPanelWindow.xaml.cs:573-576`）与 `DynamicTrayController.cs:306` 的同类订阅**都没有对应的退订**，其正确性完全依赖"模块每次返回新节点"这一**未写进 `IModule` 契约的隐含约定**。任何模块一旦为性能缓存节点树（很自然的优化），立刻退化为真实的 N 次累积泄漏。

## 3. 两份报告均遗漏的问题（15 项，本次补出）

### 3.1 🔴 新增 · `ConfigEditorWindow` 保存会静默重置悬浮面板全部设置

**路径**：

```csharp
// Views/ConfigEditorWindow.xaml.cs:250-270  BuildCurrent()

s.IdleMinutes = idle; ... s.Language = ...; s.ExcludeProcesses = ...;

// :312-328  DoSave()

```

`AppSettings.CopyTo`（`Models/AppSettings.cs:43-61`）**包含** `FloatingPanelHotkey / Position / Pinned / Locked / X / Y`。因此只要用户在配置编辑器里点一次「保存」或「保存并应用」：

- 自定义悬浮面板热键被重置为 `"Win+Alt+C"`（并因 `ReloadConfig` → `RegisterFloatingPanelHotkey` 立即重新注册默认热键）；
- `Position` 重置为 `"Tray"`、`X/Y` 回到 `-1`、钉住与位置锁全部取消。

**影响**：用户可见且**静默**（无任何提示），属于配置数据丢失。两份报告都只审了 `ConfigEditorWindow` 的语言/`App.Config` 直连，没走 `DoSave` 的字段覆盖路径。

### 3.2 🟠 升级 · `ConfigService` 配置损坏是「静默重置 + 下次覆盖」，比 bd 描述更严重

bd §7.5 写的是"`LoadOrCreate` 未见损坏分支（未加 `.corrupt` 备份）"。实测更糟：

```csharp
// ConfigService.cs:135-180  ReadFile()
catch
{
    // 若解析异常，安全回退到默认设置
}
return new AppSettings();      // ← 损坏内容被静默丢弃，Current 变成全默认
```

随后 `App` 的任意一次 `Save()`（托盘勾选项、模块 `SaveModuleConfig`、退出…）都会把这份默认值写回 `config.json`，**原始损坏文件永久丢失**，且用户只看到"设置全没了"。

**建议**：原子写落地时同步加损坏自愈——解析失败先 `File.Copy(FilePath, DirPath/".corrupt-{yyyyMMddHHmmss}.json")`，记 `LogError`，再回落默认值并在托油气泡提示。

### 3.3 🟠 新增 · `TaskConfigService` 同样非原子写

bd 只点了 `ConfigService.Save`。`tasks.json` 走的是同一模式：

- `TaskConfigService.cs:151` `File.WriteAllText(FilePath, json, Encoding.UTF8)`（`Save`）
- `TaskConfigService.cs:51` `File.WriteAllText(FilePath, sample, ...)`（首次生成）
- `TaskConfigService.cs:68` `File.WriteAllText(SampleFilePath, sample, ...)`

任务配置文件被 TaskEditorWindow 频繁重写，掉电/半写会直接损坏任务定义。应复用同一套 temp+replace 原子写工具。

### 3.4 🟡 新增 · `App.OnAppExit` 从不调用 `Services.Dispose()`，`ServiceContainer.Dispose` 是死代码

`App.xaml.cs:445-461` 手工释放了 `ForegroundTracker`、`AudioService`、`_tbIcon`、`_mutex`，但**没有** `Services?.Dispose()`。因此 `ServiceContainer.Dispose()`（`:120-141`，含逆序释放 + `_disposed` 去重保护）形同虚设，`HostPinService` / `ConfigManager` / `DefaultLoggerService` / `SystemIdleService` 都不走容器释放路径。

当前这些类型多数无可释放资源，但契约上是漏洞。建议 `OnAppExit` 末尾补 `try { Services?.Dispose(); } catch { }`，并移除散落的手工释放。

### 3.5 🟡 新增 · `ServiceContainer.ResolveAll` 持锁调用工厂 → 潜在死锁

`Host/Services/ServiceContainer.cs:90-116`：`lock (_lock)` 内部执行 `reg.Factory(this)`（`:106`）。若任何工厂回调容器（`AddSingleton` / `GetService`），而 `Dictionary` 的锁不可重入则会死锁。当前注册的都是预构建实例（无工厂回调容器），属**契约风险**而非现存 Bug。建议把锁收敛为"只在字典读写区间内持有"。

### 3.6 🟡 新增 · `SystemIdleService` 用时钟奇偶做 2s 降频

```csharp
// SystemIdleService.cs:93-97
if ((DateTime.UtcNow.Ticks / TimeSpan.TicksPerSecond) % 2 == 0) PollBusy();
```

依赖"1s 定时器与墙钟秒奇偶的相位对齐"。定时器抖动/系统时间调整时会连续两次命中或整秒跳过 → `SystemBusyChanged` 广播时点漂移。应改为内部 tick 计数器 `if (++_tick % 2 == 0)`。

### 3.7 🟡 新增 · `SystemIdleService` 首个 tick 不会触发 `UserActiveDetected`

```csharp

TimeSpan raw = GetRawIdle();
bool prevActive = RawIdle <= TimeSpan.Zero;   // 初值 RawIdle == Zero → prevActive = true
RawIdle = raw;
if (raw <= 1500ms && prevActive == false) _userActiveHandlers?.Invoke();
```

首 tick 时 `prevActive` 恒为 `true`，即使用户正在操作也不会广播一次活跃事件。对"启动后立即重新武装闲时状态机"的语义有细微偏差（模块的 `ResetIdleMachine` 依赖该事件）。

### 3.8 🟡 新增 · AppAutoMute 白名单模式下空 `TargetApps` 直接短路

```csharp
// AppAutoMuteModule.cs:184-185
if (string.IsNullOrEmpty(procName) || Config == null
    || Config.TargetApps == null || Config.TargetApps.Count == 0) return;
```

白名单的语义应是"除白名单与前台外全部静音"，空白名单 ⇒ "除前台外全部静音"；但代码在列表为空时**完全不静音**。黑名单模式下该短路是合理的，白名单模式下语义相反。应仅在黑名单模式短路。

### 3.9 🟡 新增 · `AppAutoMuteSettingsWindow.OnSaveClick` 在模块未初始化时写出孤立配置

```csharp
// Views/AppAutoMuteSettingsWindow.xaml.cs:193-208
```

### 3.10 🟡 新增 · `ProfileScheduleEngine` 同步/异步路径并发触碰 DDC/WMI

`_isApplying` 门（`MonitorDdcService.cs:95,127-132`）只保护 `SetBrightnessAndContrastAsync` 队列。而 `ApplyCurrentSettingSync`（`ProfileScheduleEngine.cs:190-205`）经 `SetBrightnessAndContrastSync` **绕过该门**，且由 `ScheduleDelayedReapply`（`:109-122`）在 `Task.Run` 线程池上调用。于是"唤醒重试"与"定时器/热键触发的异步应用"可能并发调用 `dxva2` / WMI，出现物理显示器句柄竞争。建议 sync 路径也纳入同一把锁。

### 3.11 🟡 新增 · `HotkeyService` 静态单例永不释放

`HotkeyService.Dispose()`（`:143-158`）销毁句柄并清空映射，但**未把 `_instance` 置 null**。容器释放后静态实例仍存活，`Instance` 属性会返回一个已 `DestroyHandle` 的对象；后续调用 `Register` 因 `_created` 仍为 `true` 而走到 `RegisterHotKey(this.Handle, ...)`（句柄已失效）。

### 3.12 🟡 新增 · `AwakeService` 命中即 `break`，同一进程名的整个 `Process[]` 都不释放

`AwakeService.cs:306-311`：`break` 跳出时，`Process.GetProcessesByName(nameOnly)` 返回的数组里其余元素同样未被 Dispose（C2 的精确表述）。修复时应对**整个数组**逐个 `Dispose`（或统一 `using`）。

### 3.13 🟡 新增 · `ApplyCurrentSettingSync` 无条件 `NotifyApplied`

```csharp
// ProfileScheduleEngine.cs:202-204

NotifyApplied(...);      // ← 未校验 res，失败也对外广播"已应用"

```

与 B5（异步路径假成功）是同一类"UI 状态先于硬件事实"的问题，但这份报告没提同步路径。

### 3.14 🟡 补强 · LockWindow 的物理像素/DIP 是**同一窗口内混用**，比 gm 描述的更棘手

gm 只说了构造函数的 `Left/Top/Width/Height` 未做 DPI 换算。实测该窗口两套单位并存：

| 位置 | 单位 |
|---|---|
| `LockWindow.xaml.cs:64-67` 构造 `Left/Top/Width/Height` | WPF **DIP** |
| `:105` `SetWindowPos(hwnd, TOPMOST, _bounds.Left, _bounds.Top, _bounds.Width, _bounds.Height, ...)` | Win32 **物理像素** |
| `:149,198,301` 其余 `SetWindowPos` | 不传尺寸（`SWP_NOMOVE\|SWP_NOSIZE`），无冲突 |

即：非 100% 缩放下，构造函数设 DIP 值、`OnSourceInitialized` 又用物理值覆盖同一个 HWND，随后 WPF 布局可能再按 DIP 回写 → 尺寸在两者间摆动。修的时候要**统一口径**（推荐全走 DIP + `PresentationSource.CompositionTarget.TransformToDevice` 反算，并保持 `SetWindowPos` 不再传宽高）。

### 3.15 🟡 关联 · `IdleDetector` 同时是"半死代码"与"正确 QUNS 常量的唯一现存处"

`Services/IdleDetector.cs:9-17` 的私有枚举 `QUERY_USER_NOTIFICATION_STATE` 正是 B1 所需的正确值（`RUNNING_D3D_FULL_SCREEN = 3`、`PRESENTATION_MODE = 4`、`ACCEPTS_NOTIFICATIONS = 5`、`QUIET_TIME = 6`）。清理该文件时**不要连常量一起丢**——B1 的修复应直接采用这组值。

## 5. 明确不做 / 维持现状的决策

| 议题 | 决策 | 依据 |
|---|---|---|
| 引入 MEDI（`Microsoft.Extensions.DependencyInjection`） | **不做** | 服务约 10 个、无 Scope/泛型校验需求；手写容器已具备多注册/`GetServices`/`Dispose`。引入 200–300KB 体积 + 绑定重定向维护链，收益为负。切换阈值：服务超 20 个或出现 Scope 需求 |
| 进程外插件 / 热插拔 | **不做** | net48 无 ALC、DLL 锁定不可卸载、无隔离；真要插件市场应走进程外 mini-host + IPC |
| `KeyboardBlocker` 放开字母 PIN | **待定**（P2-6 需产品决策） | 涉及既有 PIN 兼容性，`FirstRunWindow` 校验与钩子策略必须同步改 |
| `AwakeModule` 重启恢复上次 Awake 状态 | **维持当前取舍**（仅补注释） | 恢复"无限保持"会在用户无预期时阻止休眠，风险高于收益 |
| `App` 静态门面 `Services` / `Modules` 保留 | **保留** | 作为 Host 入口的引导点合理，但 `ScreenLockMod` 等 5 个别名与 `Config` 强转必须清除（P1-2） |
