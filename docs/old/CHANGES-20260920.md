## 2026-09-20 09:23 — 代码审查 P2 修复（批次 C）：架构收口与退出守卫

- **P2-14 服务容器定向解析**（`ServiceContainer.cs`）：`GetService` 原先调用 `ResolveAll()` 后取 `[0]`，会把该类型下**所有**注册都实例化一遍——用一次解析的代价构造全部实例并触发其副作用。改为只解析第一个匹配项；`GetServices` 保留"解析全部"的语义，`TryGetService` 改为复用 `GetService`（行为一致但不再重复实现解析逻辑）。抽取 `Resolve(Registration)` 供两条路径共用。
- **P2-13 移除残留静态配置门面**（`App.xaml.cs`）：0918 已完成调用点迁移，但 `App.Config` 与公开的 `App.Services` 仍以 public 形式存在，是"宿主零感知"铁律最容易被再次绕过的捷径。现删除 `Config`、把 `Services` 收窄为 private（App 内部装配与回调仍可用），并注释说明缘由。App 内部仅剩 2 处对旧门面的引用，改为经注入的 `_configManager`。
- **P2-17 模块释放契约补齐**（`ScreenLockModule` / `AwakeModule` / `TaskSchedulerModule`）：三个模块此前均未覆写 `Dispose`，导致其持有的服务与**静态事件**永不释放——LockController（静态 `SystemEvents.DisplaySettingsChanged` + 全局键盘钩子）、AwakeService（1 秒 `DispatcherTimer` + 5 个事件订阅，Initialize 时订阅从未解绑）、TaskSchedulerService（静态 `SystemEvents.PowerModeChanged`）。现均补 `Dispose` 覆写并成对解绑事件；`ClipboardHistory` 与 `MonitorProfile` 原本已实现。
- **P2-18 托盘投影的事件生命周期**（`MenuProjectionEngine.cs`）：对模块侧 `TrayMenuItem` 的 `Children.CollectionChanged` / `PropertyChanged` 订阅原先用裸 lambda 且从不解除，依赖"模块每次重建节点树"这一脆弱约定——一旦模块改为复用/缓存节点，订阅会随打开次数线性累积，触发 N 倍 `RequestRefresh` 的递归刷新风暴。现改用具名处理器，并以视觉元素的 `Unloaded` 作为订阅生命周期边界（未卸载时退化为原行为，即随节点一起被 GC，不会更差）。
- **P2-15 退出守卫不再冻结 UI**（`SafeInvoker.cs` / `App.xaml.cs`）：`PromptExit` 在托盘点击处同步调用 `task.Wait(3s)`，逐个守卫叠加最多阻塞 UI 线程 3×N 秒，表现为"点退出像卡死"。新增 `RunTimeoutAsync`（超时同样视为放行、留痕 `TimeoutException`、完成后回到 UI 线程可安全继续操作界面），`PromptExit` 改为异步协商。同步版 `RunTimeout` 保留并在注释中标注"仅限非 UI 线程"。
- **验证**：新增 8 个用例（`HostServiceTests.cs`）——`GetService` 只实例化第一个注册、`GetServices` 仍解析全部、`TryGetService` 与 `GetService` 语义一致、共享实例只被释放一次；`RunTimeoutAsync` 的正常完成/超时不阻塞/异常留痕/空 action 四种路径。全量 181 项通过。

## 2026-09-20 09:11 — 代码审查 P2 修复（批次 B）：配置持久化的正确性与自愈

- **P2-2 配置编辑器重复落盘**（`ConfigEditorWindow.xaml.cs` / `ConfigManager.cs`）：`SaveModuleConfig` 新增 `persist` 参数，批量场景先只更新内存、最后由调用方统一 `Save()`。此前一次保存会连续触发 3 次全量写盘 + `File.Replace`（两次模块写 + 一次整体写）。
- **P2-3 "恢复默认"只改控件不改模型**（`ConfigEditorWindow.xaml.cs`）：
  - 根因：原实现用一组临时默认值对象逐个赋给控件，却完全没有同步 `_editing` / `_editingScreenLock` / `_editingTaskScheduler` 三个数据模型。凡是**未暴露在界面上**的字段，都会在保存时（`SyncFromUI` 之后 `_editing.CopyTo`）把旧值原样写回，"恢复默认"因此只对界面上可见的那几个字段有效。
  - 修复：抽出唯一的"模型 → 界面"通道 `ApplyEditingToUi()`（`LoadCurrent` 与"恢复默认"共用，消除两条路径的不对称），"恢复默认"直接改数据模型后经该通道刷新界面。
  - 明确划定范围：PIN（安全凭据，清掉会把用户锁在门外）、Language（语言偏好，重置会导致界面语言突变）、FloatingPanel*（窗口位置/钉住/锁定属窗口状态而非配置默认值）**刻意不在恢复范围内**，并在代码中注明理由。
- **P2-4 PIN 服务 pending 与 current 语义分叉**（`HostPinService.cs`）：`Salt`/`Hash`/`IsConfigured` 优先读 pending，而 `Verify` 无条件 `BuildFromCurrent()`。只要出现"设置了新 PIN 但尚未写盘"的状态，就会出现界面显示已配置、输入正确 PIN 却永远失败的诡异现象。现在 `Verify` 与其余访问器采用同一优先级（有 pending 用 pending），并在升级哈希落盘后同步 pending，回到单一来源。
- **P2-5 任务配置损坏不自愈 + 无 schema 版本**（`TaskConfigService.cs` / `TaskSchedulerService.cs`）：
  - 损坏文件原先只被复制成 `tasks.corrupt-*.json`，`tasks.json` 本身仍是坏文件：下次启动继续失败、永远不恢复。现在备份后重建一个可用的空任务文件，并通过 `FileRecovered` 让上层**弹通知告知用户备份路径**（此前用户只会看到"任务列表突然清空"而不知备份在哪）。
  - 补上 schema 版本语义：新增 `CurrentSchemaVersion` 常量与 `TaskLoadResult.SchemaVersion`，明确"**字段缺失即视为 v1**"（历史裸数组格式本就没有版本标记），读取端同时接受裸数组与 `{ "version": n, "tasks": [...] }` 信封，遇到不认识的更高版本会留痕但仍尽力解析。
  - `ParseTasksJson` 内部会吞掉异常只记错误，导致"顶层结构都解析不了"时外层回滚逻辑不触发；现由 `DetectSchemaVersion` 显式返回 -1 判定损坏。
  - 空 `tasks.json` 不再被静默当作"零任务"接受，而是记录错误。
  - **有意不做**：写入端仍保持裸数组格式，不改成版本信封——tray 提供"编辑 tasks.json"，改顶层形态属影响可手改文件格式的变更，需要单独决策。
- **P2-6 孤儿临时文件**（`AtomicFile.cs` / `ConfigService.cs`）：核查确认 `AtomicFile.WriteAllText` 的 `finally` 已保证正常路径不泄漏（历史残留来自进程被强杀）。新增 `CleanupStaleTempFiles`：仅匹配本类生成的 `<名字>.tmp.<32位十六进制>` 形态、且仅删除超过 1 小时的文件，避免误删正在写入的临时文件；在 `LoadOrCreate` 启动时调用。
- **验证**：新增 8 个用例（`ConfigPersistenceTests.cs`）——只清理过期且形态匹配的临时文件、目录缺失时空操作、损坏文件备份内容完整且重建后可无错加载、空文件必须报错、schema 版本的"缺失即 v1 / 信封可读 / 更高版本留痕"、pending PIN 未落盘时可校验。全量 173 项通过，配置编辑器 UI 离屏渲染截图确认无回归。

## 2026-09-20 09:00 — 代码审查 P2 修复（批次 A）：并发安全与模块状态机

> 依据 `docs/CODE-REVIEW-20260919.md` 的 P2 清单，按模块分批修复，每批以全量单元测试通过为准提交。
> 说明：P2-12（App 反向依赖全部业务模块，需引入模块工厂并改造启动流程）与 P2-16（统一各模块设置入口，属 UX 重构）改动面与影响面过大，本批暂缓，留待单独评估。

- **P2-7 闲时服务并发与生命周期**（`SystemIdleService.cs`）：
  - 委托字段的订阅改为加锁：`+=`/`-=` 编译为 `Delegate.Combine` 后整体赋值，并非原子操作，而 ScreenLock / TaskScheduler / Awake 分属不同调用链各自订阅，并发订阅时后写者会覆盖前者，表现为"某个模块的处理器凭空消失"。这里选锁而非无锁 CAS——订阅只发生在模块启停时（极低频），用锁换取易审计的正确性。
  - `RawIdle`（8 字节 `TimeSpan`，无法标记 `volatile`）改为以 ticks 存放 + `Interlocked` 读写，消除 32 位进程上的撕裂读；`IsSystemBusyCached` 标记 `volatile`。
  - 系统忙碌状态的轮询从 `DateTime.UtcNow 秒数 % 2 == 0` 改为按 tick 计数，消除计时抖动导致的"某些 2 秒窗口触发 0 次或 2 次"。
  - 实现 `IDisposable` 释放 `Timer`（`ServiceContainer.Dispose` 会自动释放已注册的单例），并保证释放后 `Start`/`Stop`/订阅均安全。
- **P2-8 空闲触发器重复触发**（`Triggers/IdleTrigger.cs`）：`_fired` 由 `bool` 改为 `int` + `Interlocked.CompareExchange`，使"判断并置位"成为单次原子操作。原先两次非原子访问与线程池上的 `UserActiveDetected` 交错时可能重复触发或长时间无法重新武装。
- **P2-9 任务调度器触发器竞态**（`TaskSchedulerService.cs`）：新增 `_applyLock` 串行化 `Apply`，并让 `StopTriggers` 共用同一把锁。此前 `Apply` 可从 `Start`/`Reload`/`SetGlobalEnabled`/模块配置重载四路并发进入，交错时会释放掉对方刚建的触发器、重复绑定 `Fired`、或让部分触发器失去引用而无法释放（泄漏 + 幽灵触发）。锁序固定为 `_applyLock → _lock`，现有代码无反向嵌套。
- **P2-10 文件监听缓冲区溢出后静默失效**（`Triggers/FileWatcherTrigger.cs`）：
  - `InternalBufferSize` 由默认 8KB 提升到 64KB；
  - 订阅 `Error` 事件：溢出后 `FileSystemWatcher` 内部会停止抛事件，此前完全无人接收该错误，触发器表现为"突然再也不工作了"且无任何日志；现在记录 ERROR 并在线程池上重建 watcher（延时重建以避免在自身回调里 Dispose 当前实例）；
  - 目录不存在时自动创建仍保留，但补记 INFO，便于从日志发现"监听了一个意料之外的路径"。
- **P2-11 模块状态机合法迁移**（`ModuleBase.cs` / `ModuleManager.cs`）：
  - 状态与运行标志全部加锁读写；
  - `Initialize` 幂等：仅 `Created` 允许初始化，重复调用不再把已 `Running` 的模块打回 `Initialized`（此前会让后续状态判断全部失真）；
  - `Start` 增加状态机校验（仅 `Initialized` 可启动）与 `_isStarting` 重入保护，重复 `Start` 不会二次执行 `OnStart`；
  - `Stop` 先置位再回调，重复 `Stop` 不会二次执行 `OnStop`；`Faulted` 作为终端态不再被 `Stop` 改写；
  - 明确 `ModuleManager.Dispose` 的"先停后释放"顺序，并说明 `module.Dispose()` 内的二次 `Stop` 已保证为空操作。
- **验证**：新增 9 个用例（`ConcurrencyAndLifecycleTests.cs`）——16 线程并发订阅不丢处理器、取消订阅后不再收到 Tick、重复释放安全；IdleTrigger 仅触发一次与并发阈值只触发一次；模块状态机的"未初始化不可启动 / 重复初始化不重置状态 / 重复启停幂等 / Faulted 不可启动且不被 Stop 改写"。全量 166 项通过。
