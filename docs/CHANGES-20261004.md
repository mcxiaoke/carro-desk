# 变更记录

## 2026-10-04 13:40 — 第二轮修复第八批：tasks.json 并发串行化（R12）

- `TaskConfigService` 是纯静态类，`Save`（编辑器全量覆盖写）与 `Load`/`LoadOrCreate`（调度器后台重载、自愈重建）此前完全没有互斥。`AtomicFile` 只保证单次写入自身原子，保证不了"读到的内容与写入的先后关系"，于是存在"保存成功但调度器仍用旧配置"的交错窗口。
- 三个公开入口统一加一把 `FileIoLock`；内部拆出 `*Locked` 实现避免嵌套加锁（`LoadOrCreate → Load` 走重入安全的内部调用）。临界区只含毫秒级文件 IO。

### 测试

- 新增 1 个用例：写线程持续全量覆盖 `tasks.json` 的同时，读线程 20 轮读取都必须拿到完整且无解析错误的 40 条任务。

## 2026-10-04 13:25 — 第二轮修复第七批：任务编辑器保存死锁（R11）

- **加载错误不再永久封锁保存**：加载失败的任务不会进入内存列表，直接保存会把它从 `tasks.json` 里永久删除，所以不能静默放行；但旧实现把 `MessageBox` 的 OK 当成了"取消"，用户手写错一个 cron 表达式后打开编辑器点任何保存都被拦下，唯一出路是手动改 JSON。现改为明确告知代价并让用户选择"仍然保存 / 取消"。
- **保存成功后清空加载错误**：磁盘已被内存中的合法任务整体覆盖，旧的解析错误不再成立；不清空会让同一个过期告警继续拦住本窗口后续的每一次保存。被丢弃的条目记入任务日志。
- 新增 `Tasks.LoadErrorsSaveConfirm`（zh/en）。

## 2026-10-04 13:05 — 第二轮修复第六批：任务日志 IO（R8）

- **子进程 stdout 管道被顶满**：`TaskLogger.WriteOutput` 是 `Process.OutputDataReceived` 的直接回调（线程池线程）。旧实现单条日志要在**一把静态全局锁**内完成 1 次 `Directory.Exists` + 每个文件 2 轮 (`File.Exists` + `FileInfo`) + 2 次开关文件；多任务并发输出时所有回调互相排队，回调处理速度跟不上子进程写入 → 匿名管道（默认 4KB）写满 → **子进程被阻塞挂起**，现象是"脚本莫名卡住"。
- 锁粒度降到"每个日志文件一把"，不同任务、不同文件互不阻塞；目录创建只做一次；轮转检查按路径限频（≥5 秒），并复用上次记录的字节数，避免每写一行就访问文件系统。单条日志从约 8 次文件系统操作降到 1 次开 + 1 次写 + 1 次关。

### 为什么没采用审查报告建议的"内存队列 + 单写线程"

- **异步落盘会破坏读后写一致性**：任务日志是用户可见的排障入口（编辑器"查看日志"、单测读日志断言脚本实际收到的参数），异步化会让读到内容随机缺行。
- **常开追加流与外部读取冲突**：已实测，`File.ReadAllText`（`FileShare.Read`）在存在常开写句柄时直接抛"文件正被另一进程使用"，9 个既有用例因此失败。
- 真正根治（输出回调永不阻塞 + 显式 flush 屏障）需要改调用链，留待专项评估。

### 测试

- 新增 1 个用例：日志写后立即可被 `File.ReadAllText` 读到、8 线程 × 40 行并发写入不丢行、聚合日志同步落盘。

## 2026-10-04 12:35 — 第二轮修复第五批：进程句柄的停止安全与线程占用（R7 / R13）

- **误杀无关进程树（R7）**：`taskkill /PID /T /F` 前新增 pid 归属校验 —— 用构造时记录的进程创建时刻比对当前 pid 持有者的创建时间（2 秒容差）。进程已退出、pid 被系统回收分配给无关进程时跳过 taskkill 并记日志；无法判定（权限不足等）时保守放行，保持原行为。这是本模块唯一能杀"非本模块启动的进程"的路径，原先 pid 复用会连带杀掉一整个无关子树。
- **常驻任务独占线程池线程（R13）**：等待进程退出改用 `Process.Exited` 事件（底层为线程池注册的等待回调，不占线程），不再 `Task.Run(() => WaitForExit())`。detach 模式被强制为 `timeoutSec=0` + 不可取消令牌，旧实现下每个常驻任务独占一个线程池线程直到自然退出，十几个即饱和。订阅后补 `HasExited` 竞态兜底，注册失败退回阻塞等待，绝不漏事件。
- 输出 flush 的收尾等待改为 `WhenAny` + 5 秒上限，避免在异步续体里阻塞线程池线程。

### 测试

- 新增 1 个回归用例（已实证"未修复则失败"）：进程已退出后停止必须跳过 taskkill。
- 既有 detach 生命周期 / 单实例 / 调度器注册表用例全部经由新的退出等待路径通过，覆盖了本次改动的主要风险面。

## 2026-10-04 12:15 — 第二轮修复第四批：任务启动失败的资源回收（R6）

- **僵尸进程**：进程在 `proc.Start()` 成功后即已存在，此后任何异常（典型为进程瞬退时 `BeginOutputReadLine` 抛 `InvalidOperationException`）原先只做 `handle = null`，调用方拿到 `false` 后无人持有引用 —— 进程成为无人可停止的僵尸。改为按"句柄是否已接管"分别回收：已接管则由句柄停止整棵树并释放，未接管则手动关闭作业对象 + 杀进程 + 释放 `Process`。
- **作业句柄泄漏**：`job` 原为 try 块内的局部变量，异常路径下连 `SafeJobHandle` 的终结器都等不到，句柄真泄漏；作业对象的 kill-on-close 兜底也随之彻底失效。
- `ProcessJob` 补上终结器作为最后一道防线（仅关句柄，绝不抛异常）；`proc.Start()` 返回 false 的路径也显式释放 `Process`。

### 测试

- 新增 2 个回归用例：作业对象必须声明终结器（否则句柄泄漏）、创建/重复释放幂等。

## 2026-10-04 12:00 — 第二轮修复第三批：任务调度器运行态（R4 / R5 / R10）

- **常驻任务守护链（R4）**：`IsTaskStillEnabled` 由引用相等改为按任务名匹配。每次配置重载都会重建全部 `TaskDefinition`，原先会把"重载"误判成"任务被删除"，detach 守护在重启延续阶段被静默取消——常驻任务永久失去守护，且日志原因误导用户以为是自己关掉了开关。wait 模式的重试循环同样受此影响。
- **托盘 Tasks 菜单整块消失（R5）**：`GetRecent()` 与 `Tasks` 属性改为返回快照。此前 `AsReadOnly()` 只是活视图包装，锁在返回瞬间即释放，watcher 线程并发写入时消费方遍历抛"集合已修改"，被托盘菜单构建的兜底 catch 吞掉后整个菜单消失。
- **虚假失败通知（R10）**：宿主退出时对所有运行槽置位 `StopRequested`。`killWithHost=false` 的常驻任务在句柄释放后其退出 watcher 只能拿到异常退出码，原先会被判成意外退出并弹一次"失败"通知。

### 测试

- 新增 2 个回归用例（均已实证"未修复则失败"）：配置重载后 detach 守护链继续重启、`GetRecent` 返回快照而非活视图。

## 2026-10-04 11:40 — 第二轮修复第二批：PIN 失败限流跨进程持久化（R3）

- `PinGuard` 的失败计数与封锁窗口写入数据目录下 `pin-guard.json`（原子写），进程启动后延迟读回。此前二者仅存内存，"输错 4 次 → 重启宿主 → 计数归零" 可无限试探，限流形同虚设。
- 超过 24 小时未更新的记账按"旧账作废"丢弃，避免一次手滑把用户长期挡在门外；成功校验或显式复位后删除状态文件。
- 状态文件读写失败、损坏一律降级为进程内限流，绝不让限流自身成为 PIN 校验链路的不可用点。
- 持久化为**显式启用**（构造参数 `statePath`），宿主经 `PinGuard.DefaultStatePath` 注入；未注入时保持纯内存语义，单元测试不会污染用户数据目录。
- `RemainingBlock()` 也走读回，保证刚启动的界面不会显示"无锁定"而实际直接 `Blocked`。

### 测试

- `PinServiceTests` 新增 3 例：失败计数与封锁窗口跨实例（等价重启）存活、复位后状态文件被清除、未注入路径时不落盘、状态文件损坏时优雅降级。

## 2026-10-04 11:25 — 第二轮修复第一批：锁屏安全边界（R1 / R2）

按"改动小、收益大、风险低"排序分模块落实，每批均编译（0 警告 0 错误）并跑全量单测。

### 严重（锁屏认证可绕过）

- **托盘绕过（R1）**：锁屏处于锁定态时，`ScreenLockModule.GetTrayMenuItems()` 不再输出任何菜单项。锁屏把"忘记 PIN"的风险转移给用户，不能同时留一条无需凭据的解除路径——原先可经托盘打开锁屏设置 → 关掉"启用"并保存 → `OnConfigReloaded` 执行 `Controller.Unlock()`。
- **设置窗口纵深防御（R1）**：`ScreenLockSettingsWindow` 新增由模块注入的锁定态探测，锁定期间拒绝保存；托盘点击设置入口处再拦一次，防止菜单构建后恰好发生自动锁定的竞态。
- **会话解锁免 PIN（R2）**：`UnlockOnResume` 默认值由 `true` 改为 `false`（含历史扁平字段迁移的兜底默认值与示例配置）。该路径不校验 PIN，默认开启等于"设了 PIN 也能被任何一次 Windows 会话解锁绕过"。
- **解锁留痕（R2）**：因 `UnlockOnResume` 自动解除锁屏时写审计日志，便于事后分辨锁屏被解除的来源。

### 文案

- `Config.UnlockOnResumeLabel/Desc` 改为明确标注"不校验 PIN / 跳过 PIN 校验"；新增 `Lock.SettingsBlockedWhileLocked`（zh/en）。

### 测试

- 新增 `ScreenLockSecurityTests`（4 例）：`UnlockOnResume` 默认值与 Clone 保留、设置窗口锁定守卫（含探测抛异常的兜底）、未锁定时托盘菜单不被误伤。

> 锁屏本身的真机锁定路径（全局键盘钩子 + 覆盖真实显示器的置顶窗口）刻意不在自动化测试内触发，仅断言锁定态判定所依赖的接缝。

**中危（健壮性 / 正确性）**
